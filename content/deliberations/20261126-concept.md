## 2. 今の構想

```
毎晩（自動）
  集める：Git（統合済みの成果）、SpecDock、明示して登録した成果（文章・画像）
  → 公開の方針で絞る（許可されたProduct・情報源だけ）
  → 出来事（Event）を話題（Story）にまとめる・判定する（ready / hold / discard）・持ち越す
  → 媒体ごとの骨組み（事実だけ）

朝・節目（本人の操作）
  X（日本語・英語）… 確認の画面で清書 → 本人が投稿
  Reddit（英語）   … 候補だけ。投稿先の規則を本人が確かめて投稿
  note            … 「話題が十分たまった」と知らせ、本人が始めたら構成と本文の下書き
  → 投稿したものを記録 → 使った出来事を消化済みにする
```

### 2.1 概念

| 概念 | 意味 |
|---|---|
| Event | Git・SpecDock・登録した成果から観測した事実 |
| Story | 関連するEventをまとめた、発信する価値のある話題。持ち越すのはStory |
| Draft | Storyを媒体と読者に合わせて書いた下書き |
| Publication | 実際に投稿した記録（本人が投稿のURLを記録する） |

### 2.2 要件の案

1. **公開の方針が先。** Productごとに`public` / `internal`を持ち、初期値は`internal`。許可されたProductと情報源だけを集め、LLMに渡す前に絞る。顧客の情報が絡みうるProductは対象にしない。
2. **集める範囲。** 各repositoryの統合済みの成果（mainのcommit、merge）だけ。作業用のworktreeを二重に数えない。読むだけで、Gitの状態を変えない。
3. **明示の登録。** `shipcast add`で、人間かエージェントが公開候補の成果（文章と画像）を登録できる。試作の印刷や組み立てなど、Gitに出にくいハードウェアの成果を拾うため。登録は公開の許可ではない。
4. **判定と持ち越し。** EventをStoryにまとめ、ready / hold / discardに分ける。holdのStoryは次の出来事を足して育つ（課題の発見 → 案 → 試作 → 検証を1本にする）。日数の経過は投稿の理由にせず、見直しのきっかけにする。
5. **投稿の型。** Storyの性質に合う型を選ぶ（Before/After、初めて動いた、設計の判断、失敗と学び、技術の掘り下げ、舞台裏）。確かめていない効果や意図をLLMに創作させない。
6. **出す量。** 下書きはProductごとに作るが、確認の画面では全Productを通したおすすめを1〜2件に絞る。
7. **状態。** pending → drafted → approved → published（ほかにrejected、discarded）。消化済みにするのはpublishedの時点。
8. **確認の画面。** コピー、Xの投稿画面を開く（intent URL）、画像の保存、却下、投稿済みの記録。
9. **安全の検査。** 生成の後に、NGワード、絶対path、メールアドレス、トークンらしい文字列、社内のIDを検出する。画像は許可したpathのものだけを使う。これは補助で、主の防御は1の公開の方針。
10. **状態の置き場。** repositoryの外のSQLite。

### 2.3 モデルの役割（本人の案、未決）

- 集める・分析する・判定する：Codex（GPT-6.2 Sol）。安く厳密。
- 文章を書く：Gemini（4 Neon）。日本語が美しい。

注意：今の本人の環境の決まりでは、ブラウザのGeminiを代わりに操作する道具は、本人がいるときの相談だけに使い、定期の実行からは使わない。Geminiの規約で、個人のプランの枠を第三者のscriptから使うことも禁じられている。夜の自動の処理でGeminiに文章を書かせるには、次のどれかが要る（§5の未決1）。

1. 夜はCodexで事実の骨組みまで作り、清書は朝に本人の操作でGeminiに頼む（使い道を「相談」から「文章の作成」へ広げる本人の判断が要る）。
2. Gemini APIを使う（費用が出るので本人の明示の許可が要る）。
3. 当面はほかのモデルで文章も作り、Geminiは後から入れる。

## 3. ChatGPTの批評と取捨

ChatGPTに、本人の情報を伏せて構想を渡し、批評を求めた（2026-11-26）。主な指摘と取捨は次のとおり。

| 指摘 | 取捨 |
|---|---|
| commitやIssueの数で採点すると、発信する価値とずれる。並列のエージェントの分割やcommitの方針で点数が変わる | 採る。中心の見直し |
| EventとStoryを分け、点数ではなくStoryを持ち越す | 採る |
| 7日での強制の投稿をやめ、見直しのきっかけにする | 採る |
| 漏えいの対策は、禁止の一覧より公開の許可を先にする。LLMに渡すことも外部への送信 | 採る |
| LLMの呼び出しがファイルの参照や道具の実行をできると、絞った情報だけを渡す設計が崩れる | 採る。実装で、道具を止めた呼び出しを確かめる |
| 公開候補の明示の登録を足す | 採る |
| 下書き・承認・投稿済みの状態を分ける | 採る |
| 1日の候補は全Productで最大2件 | 一部採る（§2.2の6） |
| 2時間では、SpecDockの収集、定期の実行、カードの画像を後に回す | 一部採る。カードの画像とSpecDockの収集は後に回す。定期の実行は小さいので余裕があれば入れる |
| 12点の採点表 | 採らない。最初はready / hold / discardの3分類 |
| 定期の実行では、外付けのvolumeの読み取りがmacOSの許可で失敗しうる。対話の端末での成功は確かめにならない | 採る。定期の実行の検証は、実際の定期の実行の経路で行う |
| 運用の指標（採用の率、直しの時間、却下の理由、読者の反応） | 採る。運用を始めた後に |

Geminiにも同じ批評を頼んだが、Geminiの画面の変化（パーソナライズのスイッチが見つからない）で、道具が送信の前に止まり、届かなかった。

## 4. ハッカソンでの範囲（案）

- 作る：設定、Gitの収集、明示の登録、Storyの判定と持ち越し、下書きの生成と検査、確認の画面、投稿済みの記録
- 後に回す：SpecDockとOrcaの収集、カードの画像の生成、X APIなどでの予約投稿、noteとRedditの型
- デモ：shipcast自身のrepositoryから「この投稿はshipcastで作った」という下書きを出す。非公開の話題が弾かれ、価値の低い出来事が持ち越される様子も見せる。デモには架空の設定と見本のrepositoryを使う
